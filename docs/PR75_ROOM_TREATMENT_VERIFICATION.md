# PR75 — Room-Treatment Verification and Hardware Safety Gate

## Purpose

PR75 defines the final control-plane acceptance envelope that must exist before PR74's standalone MIMO FIR runtime can ever be connected to the production speaker path.

It does **not** activate room treatment.

The PR adds two independent gates:

1. **physical-source safety declarations**, and
2. **repeat acoustic measurement verification**.

A third manual **real-hardware acceptance record** is then required before a candidate can be labeled eligible for a future live-integration PR.

No software result in PR75 can enable audio.

## Why this layer exists

PR73 proves a bounded robust frequency-domain MIMO solution.

PR74 proves that the solution can be represented as a causal finite FIR matrix and processed by a bounded realtime-safe reference runtime.

Neither proves that:

- the actual speaker/subwoofer can tolerate the acoustic control effort;
- the room behaves like the measurement model after deployment;
- a treatment that looks good mathematically produces a better measured field;
- the complete protection chain works on real hardware;
- device lifecycle events remain safe;
- the result is free of audible artifacts.

PR75 makes those missing proofs explicit instead of allowing a future live-integration PR to infer them.

## Physical-source safety declaration

Every PR74 treatment actuator requires exactly one
`MIMORoomTreatmentSourceSafetyDeclaration`.

A declaration must cover the entire 20–150 Hz treatment band and confirm:

- a safe physical operating range that includes the treatment band;
- at least **3 dB reserved headroom**;
- excursion behavior has been modeled/validated for the intended system;
- continuous/thermal behavior has been modeled/validated;
- the final protection chain is present and verified.

These are intentionally physical-system declarations, not Content Preset state.

Unknown or incomplete source safety blocks progression immediately.

Duplicate declarations also fail closed.

The declaration does not pretend that dBFS alone is a driver-excursion model. Actual excursion/thermal validation remains a hardware task.

## Repeat acoustic verification

`MIMORoomTreatmentVerifier` compares a baseline calibration campaign with a treated repeat-measurement campaign using the same:

- treatment sources;
- weighted seats;
- sample rate;
- 20–150 Hz verification band.

For each source and verification frequency, the baseline weighted mean magnitude is the original spatial reference.

PR75 then calculates:

- baseline seat-to-seat RMS error;
- treated seat-to-seat RMS error;
- spatial RMS error improvement;
- treated weighted-mean level shift versus baseline;
- worst single-seat error increase relative to the original baseline mean.

This prevents a false success where spatial variance improves only because the entire low-frequency field moved substantially up or down.

### Conservative default acceptance

The default repeat-measurement gate requires:

- at least **0.50 dB** improvement in aggregate spatial RMS error;
- treated aggregate spatial RMS error no greater than **4.0 dB**;
- no source/frequency weighted-mean level shift greater than **1.50 dB**;
- no worst-seat target-error increase greater than **1.50 dB**.

These thresholds are initial conservative software defaults and should be revisited after real-room datasets accumulate.

Missing source × seat data fails closed.

Sample-rate mismatch fails closed.

Invalid transfer data fails closed.

## Hardware acceptance record

Even a passing repeat measurement is not enough.

`MIMORoomTreatmentHardwareAcceptance` requires a manual real-system acceptance record confirming:

- long-run thermal test passed;
- final protection chain test passed;
- Stop/Start passed;
- unplug/replug passed;
- sleep/wake passed;
- audible-artifact check passed;
- source count matches the candidate;
- sample rate matches the candidate.

This record cannot be generated by the DSP designer or verifier itself.

It represents a future operator/hardware acceptance step.

## Deployment gate state machine

`MIMORoomTreatmentDeploymentGate` evaluates in strict order:

1. `blockedBySourceSafety`
2. `repeatMeasurementRequired`
3. `repeatMeasurementFailed`
4. `hardwareAcceptanceRequired`
5. `eligibleForFutureLiveIntegration`

Later evidence cannot bypass an earlier failed gate.

For example:

- a complete hardware checklist cannot override failed repeat measurements;
- excellent acoustic measurements cannot override missing excursion validation;
- complete source safety cannot bypass the need for treated repeat measurements.

`eligibleForFutureLiveIntegration` is not an active state.

It only means a future PR may consider connecting the candidate to the live graph.

## Relationship to final protection

Notch Sixty already has the production true-peak/limiter protection system.

PR75 does not move, duplicate or bypass it.

The source declaration instead requires the future treatment path to prove that the complete final protection chain remains present for the physical output topology.

A future live-integration PR must define exact ordering between:

- program DSP;
- bass management;
- MIMO treatment matrix;
- physical-output protection;
- final limiter / true-peak guard.

That ordering remains intentionally unresolved until the real output topology can be tested.

## Re-measurement workflow

The intended future product workflow is:

```text
baseline campaign
    -> PR73 design
    -> PR74 FIR compile
    -> guarded temporary hardware audition
    -> repeat campaign with identical seats/sources
    -> PR75 verification
    -> manual hardware/lifecycle acceptance
    -> candidate becomes eligible for live integration
```

PR75 implements only the analysis/gating pieces that can be proven without activating the treatment path.

## Validation

XCTest covers:

- strong spatial improvement with stable mean level -> accepted;
- apparent spatial improvement caused by a large overall level shift -> rejected;
- missing treated source × seat measurement -> fail closed;
- source-safety declarations required before any later gate;
- treatment band/headroom/model completeness requirements;
- repeat measurement required after source safety passes;
- failed repeat measurement cannot be overridden by hardware acceptance;
- incomplete hardware checklist remains blocked;
- complete hardware checklist advances only to future-integration eligibility.

CI retains PR73 and PR74 validation, builds arm64 and runs the full retained XCTest suite.

## Explicit non-goals

PR75 does not connect the MIMO FIR runtime to the live render graph or any physical output.

PR75 does not:

- connect `N60MIMOFIRRuntime` to `N60LiveNChannelRenderCore`;
- publish a treatment program to realtime audio;
- add an enable switch;
- persist a live armed state;
- create a temporary audition output path;
- claim a physical device has passed hardware acceptance;
- generate a hardware-acceptance record automatically;
- implement adaptive ANC / FxLMS;
- replace final protection.

## Exit condition

PR75 can be software-complete without a Mac because it only defines and tests the acceptance machinery.

No candidate can actually reach the final hardware-accepted state until a real Mac, microphone, output devices and physical speaker/subwoofer system are available and the acceptance checklist is completed.

## Provenance

PR75 is clean-room proprietary control-plane logic built on the existing proprietary calibration and room-treatment models. It adds no third-party DSP dependency, private API, driver, helper, entitlement or network dependency.
