# E6 Unified live N-channel graph

**Status:** plan approved 18 Oct 2026 (PR #168). S2 `e6/core-skeleton` built: libn60core skeleton and versioned C ABI in `core/`, flag-independent and not linked into the app yet. S3 `e6/graph-core` built: snapshot arena, swap and retire ring, parameter mailbox, stages sanitise, meters, gain, delay, PEQ and M/S, flag `e6.unified-graph` added (off), tests `test_stages`, `test_alloc` and `test_parity`. Known follow-ups: PEQ and delay are not yet whole-buffer; the mailbox has no drain cap; meters read the newest snapshot; swap is not yet click-free. S4 `e6/dynamics-fir-stages` built: compressor, expander, dynamic EQ, program FIR and spectral denoiser stages in `core/`, ABI v3 (laneMask, new kinds, rank ordering), FFT abstraction, tests `test_dsp` and extended `test_alloc`, CI core-linux job extended. S4 limits: ABI v3; post-EQ core dynamics deferred to S5; no MidSide domain in dynamic EQ; full-complex FFT for real input left to E20; vDSP-backed FFT comes with E21; first hop after denoiser latency is a fade-in; denoiser live params 2..8; FIR taps not live.

## Goal

One realtime graph renders every mode: stereo, 5.1 and larger layouts, and binaural. Stereo is a
2-channel layout, the binaural renderer is a stage, and every lane gets the full stereo stage set.
Live parameter edits never click, and the graph rebuilds (with a short fade) only when topology
changes. `N60RenderKernel` is retired once the new graph matches it. Phase 2 gate G2: stereo is
sample-identical (within float rounding) to today's kernel on the parity suite, and live edits are
click-free on hardware in stereo, 5.1 and binaural modes.

Feature flag: `e6.unified-graph` ("Unified processing graph", epic E6), added to `FeatureFlag.all`
in S3. Flag off keeps `N60RenderKernel` and the current N-channel path exactly as today. The engine
never reads the flag: Swift decides which path to publish a snapshot to (`docs/FEATURE_FLAGS.md`).
The flag is removed in S11 together with the old path.

## What exists today

- `N60RenderKernel.c` (2,323 lines): stereo only, one call per sample frame, 32-bit float, one
  thread. Stage order is in `docs/DSP_KERNEL.md`. Snapshot type `N60DSPGraphSnapshot`.
- A separate N-channel path: `N60LiveNChannelRenderCore.h` and `N60LiveNChannelBridge.h` with
  `N60ProgramLaneEngine.h` (per-lane EQ up to 16 sections, delay up to 65,535 frames, metering),
  `N60MultichannelBassManagement.h`, `N60ProgramFIRRuntime.h`; up to 32 program channels and 40
  physical outputs. It has no dynamics, dynamic EQ, protection, M/S or ANC.
- A third path: the binaural renderer (`N60BinauralRenderer.h`, `N60HeadphoneDSP.h`) as a separate
  transport.
- Swift restrictions that exist because there are three paths: `immutableSemanticTransportActive`
  (`AudioIOEngine.swift:1377`, checked at about ten setters from line 2032), `unsupportedActiveDSP`,
  and the idle-only headphone profile rule (`AudioIOEngine.swift:2301`).

## Design note (S1)

### 1. Shape of the graph

- **Planar, block based.** All buffers are non-interleaved 32-bit float, one pointer per channel,
  processed a whole block at a time (no per-frame call). Maximum block is set when the graph is
  built and sized in time at 384 kHz (E7), not in frames. Internal state that needs it (long
  recursions, crossover, EQ at high rate) is double precision; this is the E7 rule, designed in
  from the start here.
- **Three node kinds.** (a) *Lane stage*: 1 channel in, 1 out, runs per lane. (b) *Group stage*:
  operates on a linked set of lanes (M/S pairs, linked dynamics, symmetry balance). (c) *Matrix
  stage*: N in, M out (bass management and crossover, downmix or upmix, crosstalk cancellation,
  speaker crossfeed, binaural, headphone crossfeed). The binaural renderer is a matrix stage that
  takes the virtual-speaker lanes and produces two output lanes; nothing else changes.
- **Lane stage list (fixed order, matches the kernel).** Per lane, in this order:
  1. sanitise (NaN/Inf, flush-to-zero set at callback entry per E20),
  2. input meter, input gain × headroom gain,
  3. pre-EQ dynamics (gate, expander, compressor pre-EQ members), spectral denoiser,
  4. M/S encode (group stage, only where lanes are paired: L/R, Ls/Rs, Lb/Rb, wides, heights),
  5. PEQ (up to 16 sections, plus band transitions),
  6. program FIR (partitioned; non-uniform convolver arrives in E9),
  7. M/S decode, dynamic EQ,
  8. post-EQ meter.
  Then the **matrix and system stages**: bass management and crossover, room-correction
  convolver, speaker IR convolver, ambient compensation, core dynamics with master gain,
  symmetry/crossfeed/crosstalk, balance and output gain, headphone DSP, pause gate, ANC signal
  injection, then **protection** (limiter, true-peak guard) last per output lane, then inter-channel
  delay, master gain, ANC reference capture, final sanitise and meter. Lane delay (alignment and
  user) sits just before protection in the new graph; the parity suite pins where the kernel puts it
  (inter-channel delay is after protection today) and S5 settles each difference explicitly rather
  than silently.
  The Audio Unit rack stays between the playback half and the system half, outside the core, as
  today; the host passes rack output in as lane buffers.
- **Stage templates, not virtual calls per sample.** Each stage is a C++ class with
  `prepare(rate, maxBlock)` (off the audio thread) and `process(block)` (realtime). Adjacent
  trivial stages are fused by template in E20; the stage list above is the logical order only.
- **Mode switches are topology, not code paths.** Stereo = layout {L, R}; 5.1 = six roles; binaural
  = the program layout plus the binaural matrix stage feeding {L, R}. The same graph builder
  produces all three.

### 2. Snapshot layout

- A graph is described by one **immutable POD snapshot** in a single arena allocation made off the
  realtime thread: header (`abiVersion`, `epoch`, `sampleRate`, `maxBlockFrames`, channel counts,
  stage count, total latency per output), a stage table of fixed-size records, then per-stage
  parameter and coefficient blocks addressed by 32-bit offsets (relocatable; no pointers inside).
  Heavy data (FIR partitions, HRIR spectra, delay lines, filter state) is allocated with the
  snapshot and owned by it.
- **Two kinds of update.**
  1. *Topology snapshot*: new stage list, layout, order, rate or any size change. Published with a
     single atomic pointer exchange (release on publish, acquire in the callback). The callback
     renders from the new graph and the old one is handed back through a single-producer retire
     queue; the control thread frees it after the callback has acknowledged the new epoch. The
     callback never frees.
  2. *Parameter set*: new targets for gains, biquad coefficients, thresholds, delays within
     capacity, mix amounts. Sent through a lock-free single-producer single-consumer mailbox of
     fixed-size POD records keyed by stage id and parameter index, coalesced (latest wins) at
     block start. Coefficients are designed off the audio thread; the callback only ramps.
- A parameter set that does not fit the live graph (it would change topology or exceed capacity) is
  rejected in Swift and converted into a topology snapshot, never half applied.
- **C interface (E21).** `libn60core` exposes a versioned C ABI: `n60_graph_abi_version()`,
  `n60_graph_build(const n60_graph_desc *, n60_graph **)`, `n60_graph_process(n60_graph *, const
  float *const *in, float *const *out, uint32_t frames)`, `n60_graph_post_params`, `n60_graph_retire`.
  The ABI is plain C types only, opaque handles, explicit struct sizes and an `abiVersion` field, so
  the macOS Swift shell, a Linux test host and any future shell call the same entry points. The
  existing C headers become thin wrappers during migration and are deleted as each stage moves.
- **No Apple framework in the core.** FFT through the E21 abstraction (vDSP behind it on Apple,
  PFFFT or KissFFT elsewhere), SIMD through Highway in E20, no `AudioBufferList` or Core Audio types
  in the core. Allocation, exceptions, RTTI and locks are forbidden in `process`; checked with
  RealtimeSanitizer (E20) and the realtime-reviewer.

### 3. Latency alignment

- Every stage reports its latency in frames at build time (FIR partition delay, linear-phase EQ,
  protection oversampling 32/48 frames, multirate filters, binaural). The graph builder computes
  the latency of every path to every output and inserts a compensating delay so that all outputs
  that must stay coherent (a speaker and its subwoofer, left and right, all lanes of one layout)
  share the same total latency. This generalises `upstreamProcessingLatencyFrames` in
  `N60ProgramLaneEngine.h` from one lane to the whole graph.
- Alignment groups are explicit in the snapshot. Default: all outputs of one program in one group.
  Headphone and speaker outputs, and ANC injection paths, are not forced into the program group;
  their own latency is reported, not hidden (ANC needs the exact value, section 8).
- Delay capacity is sized in time at 384 kHz (E7 lifts the 65,535-frame lane cap). If compensation
  plus user delay would exceed capacity, the build fails with a named reason and the previous graph
  keeps running.
- Total graph latency per output is published back to Swift on every snapshot swap, and changes of
  latency are themselves topology changes (they go through the fade in section 5).

### 4. Coefficient ramping

- Gains and mix amounts: linear ramp over 5 ms (32 to 4096 frames, scaling with rate) as today, now
  per block with a per-sample ramp inside the block.
- Biquads: coefficient interpolation is unsafe for high-Q low-frequency sections at 384 kHz, so a
  changed section is rendered in **parallel** (old and new coefficients, state continued from the
  old section) and crossfaded over the same ramp window, then the old one is dropped. This is
  the existing band-transition behaviour made the rule for every filter; direct form
  or transposed double-precision state in the core.
- Delays: change by crossfading two taps over the ramp window, never by jumping the read pointer.
- Convolvers: a new impulse response runs in a second convolver and is crossfaded in. The partition
  schedule is fixed, so the load is predictable (2x for the ramp window).
- Dynamics thresholds, ratios and times change instantly at block boundaries because their own
  smoothing is part of the detector; mix-type controls ramp.
- Hard rule: no parameter change may produce a discontinuity larger than the ramped step; the
  parity suite's "edit while playing" test measures this at all rates.

### 5. Rebuild with fade

- Topology changes (add or remove a stage, change layout, rate, channel mapping, FIR length class,
  alignment group, or enable the binaural stage) build a new graph off the audio thread, then run
  **old and new graphs in parallel** for a short equal-power crossfade (default 20 ms, 5 to 50 ms)
  and retire the old graph. The new graph is first run for one silent warm-up block set where state
  continuity matters (convolvers, dynamics detectors) so it does not start cold.
- While both graphs run, worst-case CPU is about 2x. The builder refuses a topology change when the
  measured per-block cost of both exceeds a budget, and Swift reports it instead of risking an
  underrun (the old graph is kept).
- If the new graph fails to build, nothing changes. If the new graph's first blocks fail the NaN
  guard, the crossfade is cancelled and the old graph stays.
- A rate change is not a fade case: it is a transport reconfiguration (the existing
  Reconfiguring state), and the graph is built for the new rate before the output restarts.
- **ANC and MIMO safety exception.** A rebuild never fades through live ANC injection. While a
  crossfade is pending the ANC stage output is muted with its 10 ms ramp in both graphs and re-arms
  only through its normal authorisation path afterwards. E6 never enables anything the E4/E19
  authorisation paths have not enabled.

### 6. Threading

- Phase 2 renders on the one existing Core Audio realtime thread. The graph is built as a **job DAG
  from the start**: each node declares its inputs and outputs, so lanes (and later MIMO and long
  convolution) can run on other realtime threads without changing the snapshot format.
- E20 adds Audio Workgroups on Apple (the equivalent realtime thread group elsewhere): worker
  threads join the device's workgroup, a lock-free ready queue schedules jobs, and a **deterministic
  join** before the output stage. Results must be bit-identical to single-thread rendering; the
  parity suite runs both.
- Control thread owns building, designing, retiring and parameter posting. Meters and diagnostics
  flow out through a lock-free ring or atomics; the callback never touches Swift state.
- Block-size invariant: the graph accepts any block from 1 to `maxBlockFrames`, so a Core Audio
  callback size change needs no rebuild.

### 7. Multirate boundaries

- The core runs at the device's native rate. Low-frequency paths may run decimated: bass
  management and subwoofer lanes, room correction below the transition frequency, ANC and MIMO
  treatment and low-frequency analysis, at 32 to 64 times below 384 kHz when E20 lands.
- A multirate region is declared in the snapshot as a **sub-graph with an explicit boundary**:
  polyphase decimator in, polyphase interpolator out, with exact group delay recorded as a stage
  latency (so section 3 aligns it) and a fixed, rate-scaled anti-alias design. The region is
  opaque to the rest of the graph; nothing inside it reads full-rate samples.
- E6 builds the boundary type and its latency accounting, and keeps every region at full rate.
  Turning a region to decimated is an E20 per-region change, each with its own parity test against
  the full-rate render.
- No sample-rate conversion exists at the transport. AGENTS.md still applies: SRC is an explicit
  DSP decision, and these boundaries are inside the DSP, not at the device.

### 8. What E4 S11 needs from E6

E4 S11 re-qualifies adaptive ANC on the unified graph. The graph must give it:
1. a **reference capture point** and an **ANC injection point** as named stages, sample-accurate
   and unchanged by rebuilds elsewhere in the graph;
2. a **reported latency** per output path in exact frames, fed to the existing feed-forward
   deadline and output-timing bridges, valid after every snapshot swap;
3. the **howl guard** and the emergency mute as graph stages that run on every block, in the
   stage order protection already uses, with the 50 ms trip budget measured at all eight rates;
4. no fade through ANC (section 5), and ANC injection **before** protection, as today;
5. the authorisation decision (`LiveANCAuthorisation`) arriving only through the snapshot;
6. multirate readiness for the ANC filter path (section 7), so S11 can compare full-rate and
   decimated ANC;
7. the E4 designs ported into the core in C++ (the S9 survey and shadow code is already
   `n60_ff_*.cpp`); the qualification campaign S8 then repeats on the graph build.
This is why S4 (core stages) places ANC injection and capture early and S11 depends on E6 S9.

### 9. Preserving shipping stereo

- Until parity holds and the owner signs off, **stereo keeps rendering on `N60RenderKernel`**. The
  unified graph is reachable only with `e6.unified-graph` on. Flag off, nothing about stereo, 5.1
  or binaural behaviour changes in any slice.
- The parity suite (S10) renders the same input through the old kernel and the new graph and
  compares them. Proposed tolerance: peak sample difference below -120 dBFS (about 1e-6) and RMS
  below -130 dBFS on every standard rate, over a fixed corpus (noise, sweeps, impulses, music
  excerpts, clipping edge cases) and a fixed config corpus (every stage on, each alone, every
  stored profile). Pure float reordering is the only allowed source of difference.
- The restrictions in `AudioIOEngine.swift` are removed only in S9, after the graph owns all three
  modes behind the flag. The kernel stays one release cycle behind its own flag after that (S11).
