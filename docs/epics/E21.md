## Goal

The engine core and the design maths build and pass their tests on Linux and Windows CI, behind
one versioned C interface, with no Apple framework in the portable sources. Swift keeps the macOS
shell, Core Audio control and UI. `AGENTS.md` states the rule.

## What exists today

- **Core library.** `core/` holds `libn60core`: the realtime graph (`core/src/graph.cpp`, the stage
  files), measurement (`core/src/measure/`, E11), room correction and bass (`core/src/correct/`,
  E10, E8 A6a), crossovers (`core/src/xover/`, E8), non-uniform FIR (`core/src/conv/nufir.cpp`, E9 S1)
  and the E19 S1 prediction (`core/src/measure/predict.cpp`). It is C++20, built with
  `-fno-exceptions -fno-rtti -Werror` (`core/CMakeLists.txt:5-12`).
- **C interface.** Four domain headers carry their own version: `N60_GRAPH_ABI_VERSION 31u`
  (`core/include/n60/graph.h:37`), `N60_MEASURE_ABI_VERSION 4` (`measure.h:21`),
  `N60_CORRECT_ABI_VERSION 4` (`correct.h:40`), `N60_XOVER_ABI_VERSION 5` (`xover.h:37`).
  `n60/fold.h` has no version. Swift reaches them through
  `NotchSixty/Audio/Realtime/NotchSixty-Bridging-Header.h:5-9`. There is no umbrella header.
- **FFT.** `core/src/fft.hpp:1-8` is the abstraction: a portable radix-2 single-precision
  transform up to `kMaxSize = 32768` (`fft.hpp:31`). No vDSP backend exists. The offline
  double FFT (`core/src/measure/offline_fft.hpp:1-17`, up to 2^24) is a separate in-house
  implementation. The only vDSP FFT in engine C is the legacy `N60Convolution.c:3, :319-369`.
- **Three source lists that have drifted.** `core/CMakeLists.txt:5-9`, `ci/core_sources.sh:4-11`
  and the Xcode target. CMake omits `fold.cpp`; `ci/core_sources.sh` and the Xcode project omit
  `measure/predict.cpp`. No workflow runs CMake or ctest, so `test_measure_predict` runs nowhere

- **Linux CI.** `.github/workflows/macos-full.yml:122-160`, job `core-linux` (nightly, or PRs

- **Realtime C outside the core.** 19 C files in `NotchSixty/Audio/Realtime/` (about 15,600 lines,
  `N60RenderKernel.c` 2,906 and `N60RealtimeAudioBridge.c` 3,501 the largest). Core Audio types

  Accelerate only in `N60Convolution.c:3`. 12 core tests (`test_*parity*.c`, `test_targeted_bridge*.c`)
  link the legacy kernel or bridges and are macOS-only by nature.
- **ANC C++ outside the core.** Eight Apple-free files in `NotchSixty/Audio/Realtime/`
  (`n60_fxlms.cpp`, `n60_remote_tonal.cpp`, `n60_ff_*.cpp`, `n60_anc_guard.cpp`,

  Their reference-lab probes are `ci/acoustic_reference_lab/e4_*_probe.c`.
- **Design maths still in Swift** (all import Accelerate on line 1 unless noted):
  measurement: `RoomCorrectionMeasurementAnalyzer.swift` (961; own `vDSP_DFT` path at :672-708

## Design note

1. **Layout.** `core/` is `libn60core`: portable sources only, under `core/src`. Platform
   backends of core interfaces live in `core/platform/<os>/` and are compiled only on that OS
   (first: `core/platform/apple/fft_vdsp.cpp`). The macOS audio backend (Core Audio bridges, tap,
   aggregate, `AudioBufferList`) stays in `NotchSixty/Audio/`; it may stay C. The macOS shell is
   Swift. A future shell links `libn60core` and writes its own backend.
2. **One versioned C interface.** Keep the per-domain versions (E11 decision: analysis changes
   never bump the realtime ABI). Add `core/include/n60/n60.h`, which includes every domain header
   and declares `n60_core_abi(n60_core_abi_info *, size_t)` reporting each domain version and
   struct size. `fold.h` gets `N60_FOLD_ABI_VERSION`. Each new domain gets its own header and
   version: `n60/anc.h` (realtime ANC), `n60/mimo.h`, `n60/speaker.h`, `n60/anc_design.h`. Swift
   checks `n60_core_abi` once at launch in Debug and in a test.
3. **One source list.** CMake is the source of truth. `ci/core_sources.sh` is generated from it
   (or replaced by a CMake build in `ci/run_harnesses.sh`); the Xcode target gets a behavioural
   XCTest that calls one entry point from every core translation unit, so a missing file fails to
   link. No text validator.
4. **Language.** C++20 baseline (`cxx_std_20`). C++23 features only once all three CI toolchains
   (Xcode clang, Linux clang, Windows clang-cl) accept them. C stays legal for tests and for the
   macOS backend.
5. **Realtime subset** (written into `AGENTS.md` in S2): no allocation, locks, exceptions, RTTI,
   `dynamic_cast`, `std::function` or other type-erased allocating wrappers, iostreams,
   `thread_local` with dynamic initialisation or function-local statics with non-trivial
   constructors on any path reachable from `process`. Off-thread design maths may allocate but
   never throws across the C boundary and is deterministic (fixed summation order, no threads,
   seeded noise). Enforcement: compile flags now, `test_alloc`, realtime-reviewer, and
   RealtimeSanitizer when E20 adds it.
6. **FFT.** One contract (`fft.hpp`), two implementations chosen at build time:
   vDSP on Apple, the in-house radix-2 elsewhere (PFFFT only if Q1 says so). Same for the offline
   double FFT. Engine code never reads a flag to pick one. On macOS, core tests run the FFT
   contract and the parity suite against both, so the portable path stays tested.
7. **Linear algebra.** In-house dense solvers in `core/src/linalg/` (Cholesky, Householder QR with
   column pivoting, one-sided Jacobi SVD; real and complex double), enough for MIMO least squares
   and Levenberg–Marquardt, unless Q2 approves Eigen.
8. **Maths moves, orchestration stays.** A Swift function moves to the core if it maps numbers to
   numbers without platform I/O (design, analysis, solvers, target-curve parsing from a string).
   Controllers, workflows, transactions, persistence and UI stay Swift.
9. **Port protocol per designer.** (a) Record Swift goldens on fixed fixtures at the eight
   standard rates. (b) Port to core behind its domain header. (c) Under `e21.core-designers` the
   production caller uses the core; off, the Swift path runs unchanged. (d) A parity XCTest runs
   both: responses within -100 dB relative error, scalar results within 1e-6 relative, optimiser
   results with the same objective within 0.05 dB and the same discrete choices. (e) The Swift
   implementation and the flag go in S14.
10. **Legacy C.** E23 deletes `N60RenderKernel.c` and what only it uses. S12 classifies every C
    file left after that: backend (stays, moves under `NotchSixty/Audio/Backend/` when touched) or
    DSP (ported to core C++ or deleted if a graph stage replaces it).
11. **Bridges.** S11 moves the Core-Audio-free parts of the bridges (snapshot acquire, fold,
    meters, deadline accounting) into a core host entry `n60_host_process` taking plain
    non-interleaved `float *const *` buffers plus a timing struct. The macOS backend only unpacks
    `AudioBufferList` and Core Audio timestamps.

## Feature flag

`e21.core-designers` (E21, off by default, added in S5): Swift production callers use the core
designers instead of the Swift ones. Off: the Swift path, unchanged. S1–S4, S11 and S12 change
no behaviour and use no flag; S3's numeric change is guarded by its parity tests. S14 removes the
flag.
