# E2 macOS 26 support

**Status:** plan approved 17 Oct 2026. S1 in review (`e2/deployment-target-26`).

## Goal

Notch Sixty builds, runs and passes its tests with a minimum of macOS 26.0, and looks and
behaves correctly on macOS 26 as well as macOS 27. This lowers the floor from 27.0 (owner
decision of 17 Oct 2026), so it needs no extra approval under the "raise the minimum OS" rule.

Feature flag: none (E1 and E2 do not need flags; the deployment target cannot sit behind one).

## What the code looks like today

- The only deployment setting is project-level `MACOSX_DEPLOYMENT_TARGET = 27.0` in
  `NotchSixty.xcodeproj/project.pbxproj` (Debug and Release). Both targets (`NotchSixty`,
  `NotchSixtyTests`) inherit it; `Info.plist` `LSMinimumSystemVersion` reads it.
- No `#available` / `@available` gates exist anywhere in Swift.
- The Liquid Glass UI (`glassEffect`, `GlassEffectContainer`, `.glass` button style,
  `ToolbarSpacer`, about 120 call sites in about 20 UI files) uses macOS 26 APIs, so it should
  compile at 26.0. The risk is how it looks on 26, not compile errors. Any 27-only API that a
  grep cannot spot will show up as a compile error once the target is 26.0.
- Core Audio process-tap APIs date from macOS 14.2 and are fine.
- "27.0" is hard-coded in release metadata, three `ci/validate_*.py` scripts and several
  workflows, which will fail once the setting changes.
- All macOS CI runs on the `xcode-27` runner label. There is no macOS 26 runner.

## Slices

### S1 `e2/deployment-target-26`: lower the floor and fix the build

- [ ] Set `MACOSX_DEPLOYMENT_TARGET = 26.0` in `project.pbxproj` (both project configs).
- [ ] Build `NotchSixty` and `NotchSixty-Performance`; fix each availability error with an
      `if #available(macOS 27, *)` gate and a 26 fallback (or `@available` on the type), keeping
      27 behaviour unchanged.
- [ ] Update the hard-coded "27.0" so existing gates stay green until E1 retires them:
      `release/pr114-commercial-metadata.json`, `release/pr114-release-baseline.json`,
      `ci/validate_pr114_release_baseline.py`, `ci/validate_final_rc_hardening.py`,
      `ci/validate_pr36_ui_foundation.py`, and the "27.0" assertions in
      `final-integrated-rc-qa.yml`, `pr114-commercial-release-candidate.yml`,
      `pr115-volume-feedback.yml`, `pr116-generate-approved-icons.yml`. Value edits only; no new
      validators.
- [ ] Add an XCTest that reads the built app bundle's `LSMinimumSystemVersion` and asserts
      `26.0`, replacing the intent of the text checks above.
- [ ] Update `README.md` (lines 17, 25) and `docs/ROADMAP.md` (lines 25, 36) to say macOS 26 is
      the minimum. Leave historical RC notes (`docs/FINAL_*`) as records; add a one-line
      "superseded by E2" note at the top of each.

Finding: the only 27-only API was `AVAudioNode.withAUAudioUnit` (8 calls in the Audio Unit
rack). They now go through `AVAudioNode.withNodeAUAudioUnit` in
`NotchSixty/Audio/AVAudioNodeAUAccess.swift`, which uses the `auAudioUnit` property on 26.

Tests: full XCTest on the dev Mac (macOS 27) via `build-test-runner`. Not engine code, so no
realtime review unless a gate lands in `NotchSixty/Audio`.

### S2 `e2/macos26-fallbacks`: check 27-only behaviour and UI on 26

- [ ] List every gate S1 added plus any API documented as changed in 27 (SwiftUI, AppKit,
      Core Audio HAL behaviour) and confirm each 26 path is sensible, not just compiling.
- [ ] Review Liquid Glass call sites for treatments that differ between 26 and 27 (materials,
      toolbar spacing, interactive glass) and add 26 fallbacks where the 26 look is broken.
- [ ] Record screenshots of the main workspaces on 26 under "Bench checks" (owner).

Findings (17 Oct 2026): building with the target temporarily at 27.0 shows one API that 27
deprecates, `AVAudioNode.auAudioUnit`, used directly in five places in the plugin editor
(`NotchSixty/UI/ProductionPluginWorkspace.swift`). Those now go through
`withNodeAUAudioUnit` as well, so the helper is the only place in the app that branches on
macOS 27 vs 26. No other API we use is deprecated in, or new in, 27. The only runtime OS-version
reads display the version string. The Liquid Glass look on 26 still needs the owner's screenshots.

### S3 `e2/ci-macos26-job`: CI on macOS 26

- [ ] Add a macOS 26 job to `.github/workflows/macos.yml` that runs the same build and test
      steps as the `xcode-27` job (and writes logs to the runner temp dir, not `/tmp`).
- **Needs the owner:** a macOS 26 runner. Either a self-hosted Mac on macOS 26 with a runner
  label (for example `macos-26`), or a GitHub-hosted `macos-26` image. The slice cannot finish
  until that runner exists.

### S4 Bench: H01–H08 on macOS 26 (owner)

See "Bench checks". Closes the epic and feeds gate G1 ("full XCTest green on macOS 26 and 27").

## Bench checks (owner, on a macOS 26 Mac)

- [ ] Install the S1 build; app launches; no missing-symbol crash.
- [ ] Grant the audio-capture permission; tap starts on the selected output.
- [ ] H01–H08 smoke cases pass (as in E3).
- [ ] Rate changes 44.1 → 384 kHz on a device that supports them; unplug/replug; sleep/wake.
- [ ] Screenshots of each main workspace on 26 compared with 27 (S2).

## Risks

- A 27-only SwiftUI API hidden in a modifier chain could need a sizeable fallback; S1 will show.
- Without a macOS 26 runner, G1's "green on 26" can only be shown by a local run on a 26 Mac.
