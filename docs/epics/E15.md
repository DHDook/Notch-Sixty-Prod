## Goal

An opt-in "Follow macOS output" mode: when the user turns it on, Notch Sixty processes whatever
output macOS is set to and recalls the Playback System bound to that output. With the mode off
(the default) nothing changes: the selected output stays authoritative, Notch Sixty never follows
the macOS default and never falls back to another device (`AGENTS.md` section 3).

## What exists today

- **Selected output.** One UID in `AudioRouteConfiguration` (`AudioRouteConfiguration.swift:3-9`),
  persisted in `UserDefaults` key `audio.selectedOutputUID` (`NotchSixtyApp.swift:98-106`).
  `selectOutput(uid:)` is a no-op unless the engine is idle (`AudioIOEngine.swift:2076-2095`).
- **Hardware events.** `AudioHardwareEventMonitor` is a final class with device-list, sample-rate,
  sleep and wake callbacks (`CoreAudio/CoreAudioError.swift:2113-2124`, `:2203-2226`). Nothing
  listens to `kAudioHardwarePropertyDefaultOutputDevice` and there is no test seam for the monitor.
- **Recovery.** A missing selected UID while running enters `recoveringOutput` and polls for the
  same UID (`AudioIOEngine.swift:5991-6012`; `AudioLifecycleState.swift:46-50`, `:80-95`). Sleep
  tears down with a fade; wake waits for the same UID (`AudioIOEngine.swift:6218-6244`).
- **Profiles.** Two layers: `ContentPreset` (`ProductProfiles.swift:103`) and
  `PlaybackSystemProfile` (`:647`) whose `PlaybackSystemState` already carries
  `associatedOutputUID` and an `activeQuietZone` configuration (`:584-602`). Selecting a system
  with a different associated UID throws `outputChangeRequiresIdle` unless idle, and rolls back on
  any failure (`:1880-1947`). Profiles needing hardware mapping are never activated
  (`:1430-1440`). The toolbar has "Associate with Current Output" and a mismatch icon
  (`ProductionProfileToolbar.swift:398-463`; `ProductProfiles.swift:1296-1300`, `:1494-1500`).
  Store: `profiles-v1.json`, atomic write (`ProductProfiles.swift:2296-2305`). Launch restore runs
  unless Safe Launch is active (`NotchSixtyApp.swift:378-382`).
- **Live treatment arming.** Never persisted (`LiveTreatmentArm.swift:127`); disarms on output
  change or loss (`:206-212`; reasons `:13-38`); the feed-forward arm anchors the output UID
  (`FeedForwardLiveArming.swift:167-174`, `:306`). Both disarm only after they observe the change.
- **Graph swap.** Same-device changes go through `UnifiedGraphHost.apply` (parameter posts or a
  20 ms faded rebuild, `UnifiedGraphHost.swift:170-179`). A device change is a full transport
  rebuild (tap, aggregate, output) at the new device's rate.
- **Policy copy** that this epic qualifies: `ProductionMetersView.swift:419`,
  `ProductionUserGuideView.swift:163`.
- **Other per-device keys** that already follow the UID and need no change: headphone device
  profile (`HeadphoneDeviceProfileConfiguration.swift:286`, `:359-363`), earned cap
  (`EarnedCapPolicy.swift:6-23`), Quiet Zone latency (`QuietZoneMeasuredLatency.swift:7-14`).

## Design note

1. **Two modes, one owner.** `OutputSelectionMode` is `.fixed` (default) or `.followSystem`.
   Fixed mode is today's code path exactly: the default-output listener is not even installed.
   With `e15.follow-output` off the mode is forced to `.fixed` whatever is stored. Only Swift
   reads the flag and the mode; the engine receives a selected UID as it does today.
2. **Notch Sixty never writes the macOS default output.** Follow mode only reads it. The user
   changes outputs in Control Centre or System Settings; Notch Sixty follows.
3. **Binding.** A new `OutputProfileBindings` table maps an output key to a
   `PlaybackSystemProfile.id`, stored as an optional field in `profiles-v1.json` and the backup
   snapshot (additive; older files load with an empty table). The key is the device UID (plus the
   data-source ID if Q2 is accepted). On first enable it is seeded from `associatedOutputUID` where
   exactly one profile names a UID; ambiguous UIDs are left unbound and listed for the user.
   "Associate with Current Output" becomes "Use for <device>", which writes both the binding and
   `associatedOutputUID`. Content presets do not follow devices (Q3).
4. **Trigger.** A default-output change (`kAudioHardwarePropertyDefaultOutputDevice`, main queue)
   while following, after a 500 ms settle window, if the resolved UID differs from the current
   selection. Repeated or same-UID notifications do nothing. Notch Sixty's own private
   tap/aggregate devices are never targets. The decision is a pure function,
   `OutputFollowPolicy.decide(event:state:) -> FollowAction`
   (`.none`, `.switchTo(uid, profileID?)`, `.pause(uid, reason)`), so every case is unit-tested
   without Core Audio.
5. **Safe switch on a running engine.** `OutputFollowCoordinator` (main actor) runs one
   transaction:
   (a) disarm every live treatment first with a new reason `.outputFollowed`
   (`LiveTreatmentArm`, `FeedForwardLiveArming`, MIMO), before any teardown;
   (b) `running → stopping`, transport teardown with the existing fade-out (new teardown cause
   `.followOutput`), `→ idle`;
   (c) `selectOutput(uid:)`; (d) apply the bound system profile through the existing
   transactional `applySystemState` (rollback on failure);
   (e) `start()`, which builds every graph, filter and asset at the new device's nominal rate off
   the realtime thread and fades in as today.
   No realtime or engine-core code changes; nothing allocates on the audio thread; all building is
   on the control plane, as for Stop/Start. If the engine was idle, steps (b) and (e) are skipped
   and the selection simply updates.
6. **Device with no usable profile.** No binding, a profile that needs hardware mapping, or a
   profile that fails to apply (for example a 5.1 arrangement on a two-channel device): Notch
   Sixty pauses processing on that output (transport stopped, so macOS plays it unprocessed),
   selects the UID so the UI is truthful, and shows "No Playback System for <device>" with
   "Choose…" and "Use current for this device". It never carries the previous device's
   correction, crossovers or bass management to a device they were not designed for (Q1).
7. **Live ANC and MIMO.** A switch never arms anything. The bound profile's Quiet Zone and MIMO
   configuration are applied disarmed; arming stays the user's action through its written
   authorisation path. The disarm in step 5a happens before teardown, so the old device never
   renders anti-noise against a stale path, and the banner says why it disarmed.
8. **What the user sees.** Settings: "Follow macOS output" (off by default) with a one-line
   explanation. While following, the output picker is read-only, "Following macOS: <device>",
   with "Stop following" (Q6). On each switch an in-app banner: "Now on <device> with <profile>"
   (plus "Quiet Zone disarmed: output changed" when relevant); on pause the sheet in note 6. No
   macOS user notifications (Q4). The policy copy in `ProductionMetersView` and the user guide
   says "unless Follow macOS output is on".
9. **Unplug, replug, sleep and wake.** Fixed mode is unchanged: wait for the same UID. Follow
   mode: losing the current device is followed by macOS picking a new default; the coordinator
   follows that default (not a guess of its own). If macOS later switches back to the replugged
   device, that is a new default change and is followed (Q5). On wake, follow mode waits up to
   3 s for the pre-sleep UID to reappear (USB and Thunderbolt re-enumerate late) before following
   a different default, so a late DAC does not flap the profile. Recovery's existing backoff and
   failure limit still apply to the chosen UID.
10. **Rates.** The new device's nominal rate is authoritative; every rate to 384 kHz is
    supported because the switch reuses `start()`. No SRC is added. Profile assets (room
    correction, HRIRs, FIRs) are redesigned or resampled exactly as on a normal start.
11. **Excluded states.** Follow mode does nothing while Safe Launch is active, during a hardware
    acceptance run, during a measurement or calibration capture, or while the engine is in
    `failed`; the pending default is applied when that state ends.
12. **Other epics.** E16 App Intents that pick a Playback System while following apply it to the
    current device and offer "Use for <device>"; they never change the output. No DSP maths
    changes in this epic, so no acoustic reference-lab case is added; the rate matrix below
    covers the eight standard rates.

## Feature flag

`e15.follow-output`, off by default. Off: today's fixed-output behaviour and UI, no default-output
listener. On: the Follow macOS output toggle and binding UI appear; the mode itself still defaults
to fixed until the user turns it on.

## Bench checks (deferred to E22)

- USB DAC unplugged while playing in follow mode: one fade-out, built-in output's binding (or
  pause) within 1 s, no burst; replugged: follows when macOS switches back.
- Same in fixed mode: unchanged recovery, no follow.
- Sleep and wake with a late-enumerating USB DAC: no profile flap; the pre-sleep profile resumes.
- Switch between devices at different rates (44.1 to 384 kHz pairs on available hardware): clean
  stop and start, correct rate in diagnostics, no click above the existing start fade.
- Quiet Zone armed, then switch output in Control Centre: disarmed before the old output stops,
  banner shown, not re-armed.
- AirPlay or Bluetooth output chosen as the macOS default: follows or pauses with a clear message,
  never falls back.

## Open questions for the owner

1. **Device with no usable profile.** Recommend pausing processing on that output with a
   "Choose…" sheet (design note 6). Alternatives: a built-in neutral system (flat, protection on),
   or keep the last profile.
2. **Binding key.** Recommend UID plus data-source ID where the device reports one, so built-in
   speakers and the headphone jack on one device (some Macs) bind separately. Alternative: UID only.
3. **Content presets.** Recommend only the Playback System follows the device; the Content Preset
   stays as the user left it.
4. **Notices.** Recommend an in-app banner only, no macOS user notifications (no new permission).
5. **Timing.** Recommend a 500 ms settle window for default changes and a 3 s wait for the
   pre-sleep device after wake; follow macOS's choice on replug rather than preferring the
   previously bound device.
6. **Manual output pick while following.** Recommend a read-only picker with "Stop following".
   Alternative: picking a device turns follow mode off.
