## Goal

An opt-in "Follow macOS output" mode: when the user turns it on, Notch Sixty processes whatever
output macOS is set to and recalls the Playback System bound to that output. With the mode off
(the default) nothing changes: the selected output stays authoritative, Notch Sixty never follows
the macOS default and never falls back to another device (`AGENTS.md` section 3).

## What exists today

- **Selected output.** One UID in `AudioRouteConfiguration` (`AudioRouteConfiguration.swift:3-9`),
  persisted in `UserDefaults` key `audio.selectedOutputUID` (`NotchSixtyApp.swift:98-106`).
  `selectOutput(uid:)` is a no-op unless the engine is idle (`AudioIOEngine.swift:2076-2095`).
- **Hardware events.** `AudioHardwareEventMonitor` is a final class with device-list, sample-rate,
  sleep and wake callbacks (`CoreAudio/CoreAudioError.swift:2113-2124`, `:2203-2226`). Nothing
  listens to `kAudioHardwarePropertyDefaultOutputDevice` and there is no test seam for the monitor.
- **Recovery.** A missing selected UID while running enters `recoveringOutput` and polls for the
  same UID (`AudioIOEngine.swift:5991-6012`; `AudioLifecycleState.swift:46-50`, `:80-95`). Sleep
  tears down with a fade; wake waits for the same UID (`AudioIOEngine.swift:6218-6244`).
- **Profiles.** Two layers: `ContentPreset` (`ProductProfiles.swift:103`) and
  `PlaybackSystemProfile` (`:647`) whose `PlaybackSystemState` already carries
  `associatedOutputUID` and an `activeQuietZone` configuration (`:584-602`). Selecting a system
  with a different associated UID throws `outputChangeRequiresIdle` unless idle, and rolls back on
  any failure (`:1880-1947`). Profiles needing hardware mapping are never activated
  (`:1430-1440`). The toolbar has "Associate with Current Output" and a mismatch icon
  (`ProductionProfileToolbar.swift:398-463`; `ProductProfiles.swift:1296-1300`, `:1494-1500`).
  Store: `profiles-v1.json`, atomic write (`ProductProfiles.swift:2296-2305`). Launch restore runs
  unless Safe Launch is active (`NotchSixtyApp.swift:378-382`).
- **Live treatment arming.** Never persisted (`LiveTreatmentArm.swift:127`); disarms on output
  change or loss (`:206-212`; reasons `:13-38`); the feed-forward arm anchors the output UID
  (`FeedForwardLiveArming.swift:167-174`, `:306`). Both disarm only after they observe the change.
- **Graph swap.** Same-device changes go through `UnifiedGraphHost.apply` (parameter posts or a
  20 ms faded rebuild, `UnifiedGraphHost.swift:170-179`). A device change is a full transport
  rebuild (tap, aggregate, output) at the new device's rate.
- **Policy copy** that this epic qualifies: `ProductionMetersView.swift:419`,
  `ProductionUserGuideView.swift:163`.
- **Other per-device keys** that already follow the UID and need no change: headphone device
  profile (`HeadphoneDeviceProfileConfiguration.swift:286`, `:359-363`), earned cap
  (`EarnedCapPolicy.swift:6-23`), Quiet Zone latency (`QuietZoneMeasuredLatency.swift:7-14`).

## Design note

1. **Two modes, one owner.** `OutputSelectionMode` is `.fixed` (default) or `.followSystem`.
   Fixed mode is today's code path exactly: the default-output listener is not even installed.
   With `e15.follow-output` off the mode is forced to `.fixed` whatever is stored. Only Swift
   reads the flag and the mode; the engine receives a selected UID as it does today.
2. **Notch Sixty never writes the macOS default output.** Follow mode only reads it. The user
   changes outputs in Control Centre or System Settings; Notch Sixty follows.
3. **Binding.** A new `OutputProfileBindings` table maps an output key to a
   `PlaybackSystemProfile.id`, stored as an optional field in `profiles-v1.json` and the backup
   snapshot (additive; older files load with an empty table). The key is the device UID plus the
   data-source ID where the device reports one (`kAudioDevicePropertyDataSource`), so built-in
   speakers and a headphone jack on one device bind separately (decision 2). On first enable it is seeded from `associatedOutputUID` where
   exactly one profile names a UID; ambiguous UIDs are left unbound and listed for the user.
   "Associate with Current Output" becomes "Use for <device>", which writes both the binding and
   `associatedOutputUID`. Content presets do not follow devices (decision 3).
4. **Trigger.** A default-output change (`kAudioHardwarePropertyDefaultOutputDevice`, main queue)
   while following, after a 500 ms settle window, if the resolved UID differs from the current
   selection, or a data-source change on the current device after the same window. Repeated or
   same-key notifications do nothing. A data-source change runs the same transaction as a device
   change (note 5), so the old profile never plays into the new endpoint. Notch Sixty's own private
   tap/aggregate devices are never targets. The decision is a pure function,
   `OutputFollowPolicy.decide(event:state:) -> FollowAction`
   (`.none`, `.switchTo(uid, profileID?)`, `.pause(uid, reason)`), so every case is unit-tested
   without Core Audio.
5. **Safe switch on a running engine.** `OutputFollowCoordinator` (main actor) runs one
   transaction:
   (a) disarm every live treatment first with a new reason `.outputFollowed`
   (`LiveTreatmentArm`, `FeedForwardLiveArming`, MIMO), before any teardown;
   (b) `running → stopping`, transport teardown with the existing fade-out (new teardown cause
   `.followOutput`), `→ idle`;
   (c) `selectOutput(uid:)`; (d) apply the bound system profile through the existing
   transactional `applySystemState` (rollback on failure);
   (e) `start()`, which builds every graph, filter and asset at the new device's nominal rate off
   the realtime thread and fades in as today.
   No realtime or engine-core code changes; nothing allocates on the audio thread; all building is
   on the control plane, as for Stop/Start. If the engine was idle, steps (b) and (e) are skipped
   and the selection simply updates.
6. **Device with no usable profile.** No binding, a profile that needs hardware mapping, or a
   profile that fails to apply (for example a 5.1 arrangement on a two-channel device): Notch
   Sixty pauses processing on that output (transport stopped, so macOS plays it unprocessed),
   selects the UID so the UI is truthful, and shows "No Playback System for <device>" with
   "Choose…" and "Use current for this device". It never carries the previous device's
   correction, crossovers or bass management to a device they were not designed for (decision 1).
7. **Live ANC and MIMO.** A switch never arms anything. The bound profile's Quiet Zone and MIMO
   configuration are applied disarmed; arming stays the user's action through its written
   authorisation path. The disarm in step 5a happens before teardown, so the old device never
   renders anti-noise against a stale path, and the banner says why it disarmed.
8. **What the user sees.** Settings: "Follow macOS output" (off by default) with a one-line
   explanation. While following, the output picker is read-only, "Following macOS: <device>",
   with "Stop following" (decision 6). Each switch or pause is announced twice (decision 4): an
   in-app banner, "Now on <device> with <profile>" (plus "Quiet Zone disarmed: output changed"
   when relevant), or on pause the sheet in note 6; and a macOS notification (note 13). The policy copy in `ProductionMetersView` and the user guide
   says "unless Follow macOS output is on".
9. **Unplug, replug, sleep and wake.** Fixed mode is unchanged: wait for the same UID. Follow
   mode: losing the current device is followed by macOS picking a new default; the coordinator
   follows that default (not a guess of its own). If macOS later switches back to the replugged
   device, that is a new default change and is followed (decision 5). On wake, follow mode waits up to
   3 s for the pre-sleep UID to reappear (USB and Thunderbolt re-enumerate late) before following
   a different default, so a late DAC does not flap the profile. Recovery's existing backoff and
   failure limit still apply to the chosen UID.
10. **Rates.** The new device's nominal rate is authoritative; every rate to 384 kHz is
    supported because the switch reuses `start()`. No SRC is added. Profile assets (room
    correction, HRIRs, FIRs) are redesigned or resampled exactly as on a normal start.
11. **Excluded states.** Follow mode does nothing while Safe Launch is active, during a hardware
    acceptance run, during a measurement or calibration capture, or while the engine is in
    `failed`; the pending default is applied when that state ends.
12. **Other epics.** E16 App Intents that pick a Playback System while following apply it to the
    current device and offer "Use for <device>"; they never change the output. No DSP maths
    changes in this epic, so no acoustic reference-lab case is added; the rate matrix below
    covers the eight standard rates.
13. **macOS notifications.** A `FollowNotifier` protocol, production
    `UserNotificationFollowNotifier` (UNUserNotificationCenter, local notifications only) and a
    test fake, injected in `NotchSixtyApp`.
    - Permission: requested once, when the user first turns Follow macOS output on (`.alert`
      only, no sound or badge); never at launch, never again after a denial.
    - Denied or not determined: the in-app banner and sheet work unchanged; Settings shows
      "macOS notifications are off for Notch Sixty" with a button that opens System Settings,
      Notifications (Notch Sixty never changes the setting itself). Authorisation is re-read
      each time the app becomes active.
    - Coalescing: one notification per settled switch, all with one request identifier
      (`e15.output-follow`) so a newer notice replaces the older one in Notification Centre; at
      most one delivery per 5 s, a later switch inside that window updates the pending notice
      and delivers it when the window ends, with the final device and profile only. The in-app
      banner shows only the latest switch.
    - Content: "Now on <device>", body "<profile>" (plus the disarm line), or "Processing
      paused on <device>: no Playback System". Clicking brings the app forward; a pause notice
      opens the "Choose…" sheet. Device and profile names stay on the Mac.
    - Posted on the main actor after the coordinator's transaction finishes; nothing in the
      realtime path, the engine or the transport knows about notifications.
    - App Sandbox: local notifications need no entitlement and no Info.plist usage string on
      macOS; `NotchSixty.entitlements` is unchanged. No push, no `aps-environment`.
14. **Source rate (S5).** What the code does today: the tap format is read and checked
    (`CoreAudio/CoreAudioError.swift:589`, `:636-646`, with adaptive SRC only for independent
    stereo clocks); the device nominal rate is only read (`Devices/OutputDeviceCatalog.swift:670-683`),
    never set; an outside change of the nominal rate is followed by the live reconfigure
    (`AudioIOEngine.swift:221-222`, `:5009-5049`, 150 ms settle, teardown and rebuild).
    - Working hypothesis, from Apple's process-tap and output-unit documentation: a player converts
      its stream to the device rate in its own process before the HAL mixes it, so the tap only
      ever carries the device (or tap) rate and never the source rate. The only real signal is a
      player that sets the DAC's nominal rate itself, and the engine already follows that.
    - Decided: the app never guesses the source rate from the signal (bandwidth or spectrum
      analysis). A wrong guess changes the DAC under the user and cannot be checked.
    - Entry rule: build automatic following on the tap only if the bench probe shows the tap format
      reporting a source rate that differs from the device's nominal rate with no device change.
      If it does, S5 records that and proposes a follow-on slice for approval; S5 itself builds
      only the probe, the tests and the finding. If it does not (expected), automatic following
      stays with V2-1 / E36 S6b (driver path), and the manual rate picker stays with E30.
    - The finding also answers E17 S9 item (a); E17 cites it there (Q7).
15. **Connections and wireless outputs (S6).** What S1–S3b already cover: a wired headphone in a
    jack that reports a data source (S2 data-source listener), and any device macOS makes the
    default (USB, Thunderbolt, Bluetooth, AirPlay). Not followed, by design (note 2): a device that
    connects without becoming the macOS default, and fixed mode. Cannot be detected: a pair plugged
    into a DAC's jack that reports no data source (picked by hand, E13 S10). S6 adds:
    - `OutputTransportKind`, read from `kAudioDevicePropertyTransportType` in `OutputDeviceCatalog`
      (built-in, USB, FireWire, Thunderbolt, PCI, HDMI, DisplayPort, Bluetooth, Bluetooth LE,
      AirPlay, aggregate, virtual, unknown), a pure mapping, and `isWireless`. Nothing in the
      app reads the transport type today.
    - Linked headphone entry (E13 G27): after the bound profile is applied (note 5d), and after a
      manual output pick, if the system's `HeadphoneList.entry(linkedTo:)`
      (`State/HeadphoneList.swift:142-143`) names the new UID and is not the selected entry, select
      it through `editSelectedSystemHeadphoneList` (`ProductProfiles.swift:1828`) using the E13 S10
      rule (live edit where it can, faded reconfigure otherwise).
    - `WirelessOutputPolicy` (pure, Swift only), for wireless outputs:
      rate is the device's nominal rate, never changed and never resampled by the app; a Bluetooth
      rate below 32 kHz is shown as "headset mode (a microphone is open)";
      new Playback Systems created for a wireless device ("Use for <device>" on an unbound device,
      or the unbound sheet) start with low-latency defaults: minimum-phase room correction,
      linear-phase EQ (E33 S27) off, total added DSP latency within a 20 ms budget (Q6);
      an existing system is never rewritten: if it exceeds the budget on a wireless output, a
      one-line note says "adds N ms on top of the <AirPlay/Bluetooth> delay" with a link to the
      setting (N from the E31 total where it exists, else the graph's reported latency);
      Quiet Zone, feed-forward ANC and MIMO arming are refused on wireless outputs with the reason
      `.wirelessOutput` (device latency is variable, so anti-noise cannot be time-aligned), and
      room, speaker and calibration measurements are refused with the same reason. Graduation
      never arms anything; this only adds refusals.
16. **Schedules (S7).** App shell and State only; no engine, Core Audio or arm code.
    - Model: `ProfileSchedule` (enabled, entries); `ScheduleEntry` (local hour and minute,
      weekdays, default every day; `ScheduledAction`; optional Playback System scope, nil means
      any). `ScheduledAction` is `.contentPreset(UUID)` and `.nightMode(Bool)`; the night-mode
      case is hidden in the UI until a `NightModeSwitching` provider exists (Q1). Stored as an
      optional field in `profiles-v1.json` and the backup snapshot; older files load empty.
      Deleting a preset removes the entries that name it. Two entries at the same minute and
      scope are refused in the editor.
    - Timeline: pure `ScheduleTimeline.next(after:)` and `latest(atOrBefore:)` over an injected
      `Calendar` and time zone. A local time that does not exist (spring forward) fires at the first
      valid minute after it; a repeated hour (fall back) fires once, on its first occurrence.
    - `ProfileScheduler` (main actor, injected clock and one-shot timer, no polling) re-plans on
      launch, wake, `NSSystemClockDidChange`, `NSSystemTimeZoneDidChange` and any schedule edit.
    - Manual change wins: at a boundary the entry's action is applied whatever the user chose
      before. Between boundaries nothing is reasserted. A preset pick, a night-mode switch, or
      later an E16 App Intent or a Shortcuts automation counts as a manual change. On launch or wake,
      if boundaries passed while quit or asleep, only the latest missed one is applied, once
      (`lastAppliedBoundary` is persisted); if none passed, a manual pick made before quitting
      survives. Turning a schedule on or editing it waits for the next boundary; the row shows
      "Next: 22:00, Cinema Night" (Q5).
    - Skips and waits: a boundary is skipped if the current preset has unsaved edits (editing is a
      manual change), or if the entry's scope is not the active system. It waits during Safe Launch,
      a measurement or calibration capture, a hardware acceptance run (once G6 lands) and `failed`,
      reusing the follow-mode block signals, and applies when the block ends.
    - Apply path: `ProductController.selectContentPreset(_:keeping:)` (`App/ProductController.swift:592`),
      the same path as a manual pick. A schedule never changes the output, the Playback System or
      any arm (Q3).
    - Notice: an in-app banner "Scheduled: <preset> (22:00)" with Undo, which restores the previous
      preset and counts as a manual change. No macOS notification (Q4).
    - UI: Settings > General, a "Schedules" card (list, add, remove, enable, next change), behind
      `e15.follow-output`, in its own view file. It works in fixed and follow modes. Screen fit per
      `AGENTS.md` section 13.

## Feature flag

`e15.follow-output`, off by default. Off: today's fixed-output behaviour and UI, no default-output
listener. On: the Follow macOS output toggle and binding UI appear; the mode itself still defaults
to fixed until the user turns it on. The same flag covers S5–S7: off means no Schedules card and no
scheduler, no linked-headphone selection, no wireless defaults or refusals, and no rate probe.

## Open questions for the owner

S5–S7 (plan PR `e15/plan-s5-s7`). Q1–Q5 must be answered before S7, Q6 before S6, Q7 before S5.

1. **Night mode in schedules.** Night mode is defined in E30 (an overlay of the E33 S15 Late night
   recipe, applied at publish time) and E30 runs after E15. Options: (A) S7 schedules content
   presets now and carries a `.nightMode` action that stays hidden until E30 injects its night-mode
   switch; E30's existing "Night mode defined" item ("E15 S7 schedules switch the same overlay")
   wires it, and S7's scope is "profile by time of day". (B) S7 builds the night-mode overlay early,
   taking that E30 item into E15 (about 600 more lines, and Dynamics page banners). (C) No night-mode
   action: users schedule the "Cinema Night" preset. **Recommendation: A.**
2. **Scope of a schedule.** (A) One global list; each entry may be limited to one Playback System.
   (B) A separate list per Playback System. **Recommendation: A** (one place to look; the scope
   covers headphones-versus-speakers evenings).
3. **What a schedule may switch.** Content presets only, never the Playback System or the output
   (systems follow the device, decision 3; a system switch can need a new output). **Recommendation:
   content presets only.**
4. **Notice for a scheduled switch.** An in-app banner with Undo, and no macOS notification (unlike
   follow switches, decision 4, because a schedule is the user's own plan). **Recommendation: banner
   only.**
5. **Missed boundaries and turning a schedule on.** On launch or wake, apply only the latest missed
   boundary, once; turning a schedule on or editing it waits for the next boundary (the row shows the
   next change). **Recommendation: as written.** The alternative, applying the current period on
   launch, would override a manual pick made before quitting.
6. **Wireless defaults.** (a) Defaults apply only to new systems created for a wireless device;
   existing systems are never rewritten and get a one-line latency note instead. (b) Added DSP
   latency budget 20 ms on wireless outputs. (c) Quiet Zone, feed-forward ANC, MIMO and measurements
   are refused on wireless outputs with a stated reason. **Recommendation: all three as written.**
7. **Source-rate finding.** S5 builds the probe, the tests and the finding only, never guesses the
   source rate from the signal, and proposes a follow-on slice only if the bench shows the tap
   reporting a source rate (expected: it does not, so automatic following stays with V2-1 / E36).
   E17 S9 item (a) cites the S5 finding in the E17 S9 PR instead of repeating the investigation.
   **Recommendation: as written.**
