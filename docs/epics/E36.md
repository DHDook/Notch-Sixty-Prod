## Goal

Notch Sixty's own user-space virtual output device, as an optional second input path beside the process tap. Apps
play into a device named for the app; Notch Sixty reads it, processes and plays to the selected DAC. With the driver:
the source rate is known, surround programme reaches a stereo DAC, the app's added delay is reported to macOS for lip
sync, and Stop gives silence instead of unprocessed audio. The app runs every v1 feature without it (AGENTS.md
section 2).

## Design note

Decisions a builder would otherwise make. Each realtime part documents allocation, synchronisation, latency, rate,
channel and reset behaviour in its PR (AGENTS.md section 4).

1. **Two repositories.** The app repository holds the input-source seam, the protocol client, the UI and the
   tests (S1–S7). The driver (X1–X3) lives in its own repository with its own installer; this repository never
   vendors driver code or binaries and never adds a workflow for it. The one shared artefact is the protocol
   (decision 3), kept as a C header and a spec in this repository and copied into the driver repository.
2. **Input-source seam.** One Swift protocol, `CaptureSource`, in `NotchSixty/Audio/CoreAudio/`, makes the
   capture device, its format and its teardown for all three sessions. `ProcessTapCaptureSource` is today's tap and
   aggregate code moved without behaviour change; `VirtualDeviceCaptureSource` opens the virtual device's input
   stream. The realtime bridge, the graph and the output IOProc are unchanged. The seam takes a `HALPropertyStore`
   protocol so tests run against a fake HAL. No code is added to `AudioIOEngine.swift`; the session factory call
   sites shrink or stay the same length.
3. **Protocol.** Versioned custom properties only (works from the sandbox): protocol version, lease, clock-rate
   scalar, DAC rate list, layout, and reported latency, on the plug-in object found by bundle ID
   (`kAudioHardwarePropertyTranslateBundleIDToPlugIn`). The app accepts a fixed list of protocol versions and
   refuses any other ("unknown driver version"). Spec: `docs/VIRTUAL_DEVICE_PROTOCOL.md`; header
   `NotchSixty/Audio/VirtualDevice/N60VirtualDeviceProtocol.h`.
4. **Lease, not a bare heartbeat.** The app renews a lease every 250 ms from a control-plane timer (never the audio
   callback). The driver publishes the device only while the lease is valid and removes it 2 s after the last
   renewal, so a crash or force-quit leaves macOS on a real output (AGENTS.md sections 2 and 5). Normal Quit fades
   out, restores the previous system output, then releases the lease at once.
5. **Clock.** The driver's clock follows the DAC by rate-scalar steering: the control plane compares
   `AudioDeviceGetCurrentTime` on both devices, filters the ratio and writes the scalar; the driver applies it in its
   zero-timestamp. Bridge fill stays bounded, so no resampling is needed. If bench shows this cannot hold, the
   existing adaptive bridge is the fallback, by owner decision only (Q9). No SRC is added by default.
6. **System output.** Switching to the driver makes it the macOS default output and stores the previous default
   output's UID (persisted, so the next launch can restore it after a crash). Switching away or quitting puts it back.
   The selected DAC stays authoritative (AGENTS.md section 3); the app refuses the virtual device as its own output,
   so it cannot feed back into itself.
7. **No silent fallback.** If the driver path is chosen and the driver is missing, has the wrong version, or
   disappears, the lifecycle enters `waitingForInputDevice` and says so; it never quietly switches to the tap. Two
   new states: `switchingInput` (fade out, change source, fade in) and `waitingForInputDevice`.
8. **Rates and channels.** The driver offers the DAC's own rates up to 384 kHz (the app writes the list) and layouts
   from stereo to 7.1.4; its channel count is a build constant of 16. Default: the app sets the virtual device to the
   DAC's rate. Automatic rate following (the player sets the rate, the app sets the DAC to match or its nearest
   supported multiple) is off by default; the v1 rate picker stays the manual choice.
9. **Indicator.** Reading a virtual device's input stream is audio input to macOS. It probably shows the orange
   microphone indicator instead of the purple capture indicator, and asks for microphone permission. This is
   unverified (bench B1) and is an owner question (Q7). The usage string gains the driver path in S5.
10. **App Store shape.** The App Store build only detects an installed driver and uses it. Its Settings sheet explains
    the add-on and opens the download page in the browser; the user runs the installer. It never downloads, runs or
    removes code (Q6).

## Slices

App repository (branch `e36/<slice>`, one PR each, behind `e36.virtual-driver`):

- [ ] S1 `e36/input-source-seam` (needs-owner: Core Audio transport, lifecycle states). `CaptureSource` protocol,
  `ProcessTapCaptureSource` moved out of the three sessions, `HALPropertyStore` with a fake, the two lifecycle states
  and their transitions, flag added. Tests: the three sessions build the same tap and aggregate descriptions as before

- [ ] S2 `e36/driver-protocol` (needs-owner: Core Audio control). Protocol header and spec, plug-in discovery,
  version gate, lease writer, driver status model (not installed, installed, needs update, unknown version, in use).
  Tests with a fake plug-in: version accepted or refused, lease cadence and release on Quit, status for each case,
  lease timer never touches the realtime path.
- [ ] S3 `e36/virtual-capture` (needs-owner: Core Audio transport, realtime bridge). `VirtualDeviceCaptureSource`,
  rate pinning to the DAC, rate-scalar steering loop, refusal of the virtual device as output. Tests with fake
  clocks at the eight rates: the loop converges within 10 s for a ±200 ppm offset, bridge fill stays within its
  bounds over a simulated 24 hours, no drops; stereo to 7.1.4 layouts carry the right channel count; 384 kHz with
  12 channels fits the fixed ring.
- [ ] S4 `e36/settings-input-path` (low-risk: UI on fakes). "Audio input path" section in the Settings window (E12
  S23 if merged, else `ProductionSettingsView` in its own file): status, the enable sheet with the download link,
  one switch between tap and driver (wired to a no-op until S5). Tests: each status renders its text and actions;
  screen fit at 1,280 x 800 and about 1,920 x 1,000 (AGENTS.md section 13).
- [ ] S5 `e36/switch-and-system-output` (needs-owner: Core Audio transport, system default output). The switch
  through `switchingInput`, default-output takeover and restore (persisted previous UID), restore on Quit before the
  lease is released, `waitingForInputDevice` on a missing driver with no fallback, silence on Stop, usage string
  update. Tests: switch both ways at the eight rates with fade-out before the source change; previous output restored
  on switch-away, Quit and next launch after a simulated crash; a missing or unknown-version driver never falls back.
- [ ] S6 `e36/driver-unlocks` (needs-owner: transport). One source-of-truth registry of features that need the driver
  and their "Needs the driver" notes (visible but unavailable without it); latency reporting from the E31 total added
  delay, kept current; surround programme on a stereo DAC through the E25 S8a fold and the E13 renderer; a
  multichannel DAC used for active stereo without Audio MIDI Setup changes; automatic rate following, off by default.
  May split into S6a (registry, notes, latency) and S6b (layouts, rate following) to stay within PR size. Tests:
  registry drives every note; latency written equals E31's total plus device latency and updates on change; 5.1 and
  7.1.4 sources fold to two feeds at the eight rates; rate following picks the same rate or nearest supported
  multiple.
- [ ] S7 `e36/ship` (needs-owner: graduates a transport flag). Driver update notice, end-to-end test through
  production wiring (Settings switch to engine, with the fake plug-in), every gap closed, `e36.virtual-driver`
  graduated. Graduated means the Settings section is available; the tap stays the default.

- **Q5 Distribution and E18.** The download page is part of the E18 website ("later the V2-1 driver download"). If

- **Q6 App Store.** Confirm with App Review that a link-only sheet is allowed (guideline 2.4.5). Fallback: status

- **Q7 Indicator.** The driver path probably swaps the purple indicator for the orange microphone indicator and
  needs microphone permission (design note 9). Is that acceptable? Recommended: yes, explained in the sheet. Avoiding
  any indicator needs a non-audio-input transport, a much larger and unproven design.
- **Q8 Crash behaviour.** After the lease runs out the device goes and macOS plays to a real output unprocessed (the
  tap path does the same today). On active speakers that is full-range audio to tweeters. Recommended: keep the
  AGENTS.md rule (the device always goes) and warn in the sheet for active setups; the alternative (device stays
  silent until relaunch) conflicts with sections 2 and 5.
- **Q9 Clock fallback.** If rate-scalar steering fails on the bench, may the driver path use the existing adaptive
  bridge (explicit, measured SRC)? Recommended: yes, shown in the signal path.
- **Q10 Bench home.** Put B1–B10 in E22 (then E22 gates on them) or keep them as E36's own point-update bench?
  Recommended: E36's own, so v1 is not held up.
