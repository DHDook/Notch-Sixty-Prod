## Goal

Notch Sixty's own user-space virtual output device, as an optional second input path beside the process tap. Apps
play into a device named for the app; Notch Sixty reads it, processes and plays to the selected DAC. With the driver:
the source rate is known, surround programme reaches a stereo DAC, the app's added delay is reported to macOS for lip
sync, and Stop gives silence instead of unprocessed audio. The app runs every v1 feature without it (AGENTS.md
section 2).

## Design note

Decisions a builder would otherwise make. Each realtime part documents allocation, synchronisation, latency, rate,
channel and reset behaviour in its PR (AGENTS.md section 4).

1. **Two repositories.** The app repository holds the input-source seam, the protocol client, the UI and the
   tests (S1–S7). The driver (X1–X3) lives in the private repository `Notch-Sixty-Prod-Driver` with its own
   installer, written from Apple's AudioServerPlugIn documentation (Q3, Q4). Sessions started here build it too.
   This repository never vendors driver code or binaries and never adds a workflow for it. The one shared artefact
   is the protocol (decision 3), kept as a C header and a spec here and copied into the driver repository.
2. **Input-source seam.** One Swift protocol, `CaptureSource`, in `NotchSixty/Audio/CoreAudio/`, makes the
   capture device, its format and its teardown for all three sessions. `ProcessTapCaptureSource` is today's tap and
   aggregate code moved without behaviour change; `VirtualDeviceCaptureSource` opens the virtual device's input
   stream. The realtime bridge, the graph and the output IOProc are unchanged. The seam takes a `HALPropertyStore`
   protocol so tests run against a fake HAL. No code is added to `AudioIOEngine.swift`; the session factory call
   sites shrink or stay the same length.
3. **Protocol.** Versioned custom properties only (works from the sandbox): protocol version, lease, clock-rate
   scalar, DAC rate list, layout, and reported latency, on the plug-in object found by bundle ID
   (`kAudioHardwarePropertyTranslateBundleIDToPlugIn`). The app accepts a fixed list of protocol versions and
   refuses any other ("unknown driver version"). Spec: `docs/VIRTUAL_DEVICE_PROTOCOL.md`; header
   `NotchSixty/Audio/VirtualDevice/N60VirtualDeviceProtocol.h`.
4. **Lease, not a bare heartbeat.** The app renews a lease every 250 ms from a control-plane timer (never the audio
   callback). The driver publishes the device only while the lease is valid and removes it 2 s after the last
   renewal, so a crash or force-quit leaves macOS on a real output (AGENTS.md sections 2 and 5). Normal Quit fades
   out, restores the previous system output, then releases the lease at once.
5. **Clock.** The driver's clock follows the DAC by rate-scalar steering: the control plane compares
   `AudioDeviceGetCurrentTime` on both devices, filters the ratio and writes the scalar; the driver applies it in its
   zero-timestamp. Bridge fill stays bounded, so no resampling is needed. If bench B4 shows this cannot hold, the
   existing adaptive bridge (explicit, measured SRC) is the approved fallback, shown in the signal path (Q9). No
   SRC is added by default.
6. **System output.** Switching to the driver makes it the macOS default output and stores the previous default
   output's UID (persisted, so the next launch can restore it after a crash). Switching away or quitting puts it back.
   The selected DAC stays authoritative (AGENTS.md section 3); the app refuses the virtual device as its own output,
   so it cannot feed back into itself.
7. **No silent fallback.** If the driver path is chosen and the driver is missing, has the wrong version, or
   disappears, the lifecycle enters `waitingForInputDevice` and says so; it never quietly switches to the tap. Two
   new states: `switchingInput` (fade out, change source, fade in) and `waitingForInputDevice`.
8. **Rates and channels.** The driver offers the DAC's own rates up to 384 kHz (the app writes the list) and layouts
   from stereo to 7.1.4; its channel count is a build constant of 16. Default: the app sets the virtual device to the
   DAC's rate. Automatic rate following (the player sets the rate, the app sets the DAC to match or its nearest
   supported multiple) is off by default; the v1 rate picker stays the manual choice.
9. **No capture indicator (owner requirement, Q7).** The driver path must show no indicator at all, neither the
   purple capture nor the orange microphone one. Risk: opening the virtual device's input stream is audio input to
   macOS and almost certainly shows the orange indicator and asks for microphone permission, so a plain loopback
   input stream does not meet the requirement. Open design item G1, settled by a spike at the start of S1 (app side)
   and X2 (driver side) before S3 is built. Candidates, in order:
   - **A. Shared-memory ring, no input stream.** The driver writes the mixed programme into a lock-free ring in
     shared memory; the app's output IOProc reads it directly. Handshake by a Mach service the plug-in may look up
     (`AudioServerPlugIn_MachServices` in its Info.plist), vended by the app through an app-group-named service
     (for example a bundled login item via `SMAppService`). Questions: does the sandbox allow both ends, and does
     the plug-in host allow the mapping.
   - **B. A file-backed ring in a location both sandboxes can map.** Fallback if A's Mach handshake is refused.
   - **C. A device or stream property that makes the HAL treat the read as non-input.** Bench probe only; not
     expected to work.
   - Rejected: a process tap on the virtual device (purple) and a plain input stream (orange).
   If none works, the owner decides how the epic continues. With A or B, one IOProc (the DAC's) both reads the ring
   and plays, and S3's capture source is the ring reader.
10. **App Store shape.** The App Store build only detects an installed driver and uses it. Its Settings sheet explains
    the add-on and opens the download page in the browser; the user runs the installer. It never downloads, runs or
    removes code. Whether App Review accepts the link is Q6, deferred to S7.
11. **Crash warning (Q8).** The device-disappears rule stays. The Settings sheet warns users with active speakers
    (no passive crossover) that after a crash macOS plays to a real output unprocessed.

## G1 spike, app half (S1, 22 Nov 2026)

Desk study only: no hardware, no driver, nothing installed or run. Result: **no transport is chosen yet**; S3 stays blocked.

- **A (shared-memory ring + Mach handshake).** App side needs the sandboxed app to look up a service the plug-in
  registers (`com.apple.security.temporary-exception.mach-lookup.global-name`, a temporary exception App Review may
  refuse) or to vend a service itself that coreaudiod's plug-in host may not be allowed to look up. The shared
  mapping name must satisfy the sandbox's POSIX shm rules (app-group prefix) that the driver, running inside
  coreaudiod, cannot use as a group member. Both ends are unproven.
- **B (file-backed ring).** The app can map a file in its container or a group container; coreaudiod's sandbox
  decides whether the plug-in can map the same file. Needs a probe with a stub plug-in (X2).
- **C (property trick).** Not expected to work; one probe call.
- **Rejected as before:** plain input stream (orange indicator and microphone permission), process tap (purple).
- **What the app already has:** entitlement `com.apple.security.device.audio-input` and the mic usage string, so a
  plain input stream would run but shows the indicator; no mach-lookup or group entitlement exists.

Probe plan (bench, with X2): one stub plug-in publishing a 1 MiB ring by A, then B; the app maps it from the sandbox;
record indicator state, entitlements needed and whether App Review risk is acceptable. Added under Bench checks.
