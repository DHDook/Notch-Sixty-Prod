## Goal

Every graph lane, stereo or N-channel, takes a program FIR, room FIR, speaker IR or driver FIR of up
to 262,144 taps (0.68 s at 384 kHz, 5.9 s at 44.1 kHz) at the same 256-frame engine latency the
stereo kernel has today, so no configuration falls back to `N60RenderKernel` because of tap count.
Every output, sub lanes included, gets the stereo chain's limiter, true-peak guard and soft clip,
and a per-output headroom assistant predicts and trims the gain each output needs.

Done when (PROGRAM_PLAN): N-channel lanes match stereo protection and 262k-tap FIR. E9 also closes
E7's "program FIR 32,768 taps" cap item.

## What exists today

- **Core FIR is uniform and capped.** `N60_FIR_MAX_TAPS = 128 × 256 = 32,768`
  (`core/include/n60/graph.h:387–388`, doc :271–277). `runFir` (`core/src/stages_dsp.cpp:809`)
  calls `firStep` (:779) per sample; every 256 frames it does one 512-point FFT, a multiply-add over
  all partitions (128 at the cap) and one inverse FFT, all in one tick. ROOM_FIR, SPEAKER_IR and
  DRIVER_FIR run as FIR (`core/src/snapshot.cpp:237–240`). Two-band ROOM_FIR (E10 S3/S8,
  `stages_dsp.cpp:833–873`, :938) caps each band at 32,768.
- **FFT.** `core/src/fft.hpp:31` full-complex plans up to 32,768 points; no real-input transform
  (E20).
- **State carry and warm-up.** `adopt` (`core/src/graph.cpp:197–225`) runs on the realtime thread
  and calls `dspFirCarry`, a memcpy of each unchanged FIR's lane history (about 263 KB per lane at
  32,768 taps; it would be about 2 MB at 262,144). A new or changed FIR warms for its full tap
  length before the crossfade (`graph.h:274–277`, `firWarm`).
- **Legacy stereo convolver.** `NotchSixty/Audio/Realtime/N60Convolution.h:11–48`: non-uniform,
  three segments (256 × 4, 1,024 × 4, 4,096 × up to 63), 262,144 taps, 256-frame latency, older
  partitions' multiply-adds spread across the block. It uses vDSP (`N60Convolution.c:3, 319, 369`), so
  the core cannot link it. The legacy N-channel `N60ProgramFIRRuntime.h:22` is uniform and capped at
  32,768.
- **Swift caps at 32,768.** `UnifiedGraphProgramDSP.swift:216` (program FIR), :276 (delta FIR for
  latency alignment), :297 (room lane plan); `UnifiedGraphTranslator.swift:137`;
  `UnifiedGraphConfiguration.swift:207`; `N60UnifiedGraphEligibility.h:355–360` (kernel fallback
  above 32,768). Designers that choose two-band above 32,768: `core/src/xover/xover.cpp:338–350`,
  :590; `core/src/correct/synth.cpp:31` (`kStageMaxTaps`); Speaker Optimizer via
  `N60_PROGRAM_FIR_MAX_TAPS` (`SpeakerOptimizerFIRDeployment.swift:120, 377`).
- **Protection.** PROTECTION is linked over its lane mask (`graph.h:334–340`,
  `core/src/stages_system.cpp:1635`). Layout graphs apply it to program lanes only
  (`UnifiedGraphProgramDSP.swift:381–390`, `mask(0..<count)`), so sub lanes are unprotected (E6 D2
  table, `docs/epics/E6.md:684`, "sub lanes stay E9"). E8's routed outputs already get one
  PROTECTION stage per output (`SpeakerRoutingCompiler.swift:288–294`).
- **Headroom.** Stereo-only and conservative: `conservativeAutomaticHeadroomDB` sums positive band
  gains (`StereoPlaybackControl.swift:228`), `AutomaticHeadroomConfiguration`
  (`DynamicsConfiguration.swift:1005`, off by default). No per-output analysis exists.
- **Flags.** No `e9.*` flag (`NotchSixty/State/FeatureFlags.swift:21–117`).
- **Tests.** `core/tests/test_dsp.c:341, 553–615` (FIR, 32,768 build and +1 rejection),
  `test_rebuild.c:775` (carry), `test_alloc.cpp`, `test_parity_suite.c` (goldens),
  `NotchSixtyTests/ConvolutionTests.swift:657` (legacy 262,144), `ci/benchmark_nonuniform_convolution.c`.

## Design note

1. **One non-uniform engine in the core.** New `core/src/conv/` (C++, `fft.hpp` only, no Apple
   framework) implements non-uniform partitioned convolution with zero added delay beyond the
   256-frame base block (Gardner 1995; Garcia 2002; Wefers 2015). The schedule matches the legacy
   convolver, 256 × 4, 1,024 × 4, 4,096 × up to 63, so the cost is known and the engine latency
   stays exactly 256 frames: Swift's latency alignment, the declared-latency rule and the kernel
   hand-over are unchanged. E13 S4's `BINAURAL_TAIL` and later E19 MIMO filters reuse this engine
   with their own schedules; tuning the schedule (a 16,384 segment, for example) is E20's job, with
   benchmarks.
2. **Whole-buffer and bounded per tick.** The engine processes whole blocks in chunks up to the next
   256-frame tick (no per-sample call). The multiply-adds of older partitions in the 1,024 and 4,096
   segments are spread evenly across their block's ticks. Where a segment's offset leaves slack, its
   forward FFT, newest-partition multiply-add and inverse FFT go in different ticks. Acceptance is a
   deterministic operation counter, not timing: at 262,144 taps the worst tick is at most 2.5 × the
   mean tick. Moving the long tail to an Audio Workgroup worker thread is E20.
3. **Selection without changing flag-off output.** `n60_graph_desc` gains `firScheme` (ABI v19,
   appended): 0 = today's uniform scheme, at most 32,768 taps, bit-identical; 1 = the non-uniform
   engine for FIR, ROOM_FIR, SPEAKER_IR and DRIVER_FIR, at most 262,144 taps
   (`N60_FIR_MAX_TAPS_LONG`). Swift sets it from `e9.long-fir`; the core never reads a flag. The
   two-band stages keep their own caps, but with the flag on no designer emits them (owner, Q2). When the flag is removed, the uniform scheme and
   `firScheme` 0 are deleted with it.
4. **Unit-impulse taps run as a delay.** The engine detects a tap set that is a single 1.0 and runs it
   as a ring delay (bit-exact, O(1) per sample). The latency-alignment delta FIR
   (`UnifiedGraphProgramDSP.swift:274–279`) then costs nothing at any length, up to
   `N60_GRAPH_MAX_DELAY_FRAMES`.
5. **No unbounded copy on the realtime thread.** `dspFirCarry` becomes an amortised carry: `adopt`
   records which partitions to copy, and each callback copies at most a fixed budget (default 256 KiB
   per callback for the whole graph) while the incoming instance warms. The remaining copy time is
   added to `warmLeft`. A slot copied early stays valid because the outgoing ring only overwrites it
   a whole segment later; the test covers the wrap.
6. **Faster warm-up for a changed filter.** Partition input spectra do not depend on the taps. When a
   FIR changes but its lanes, its position, its schedule and every stage upstream of it on those
   lanes are unchanged (the usual case: the user loads a new filter), the new stage is seeded from
   the old stage's input history through the same amortised copy, so it is audible within a few
   callbacks instead of after 262,144 frames. Otherwise it warms silently for the full length, as
   today, under the existing rebuild CPU-budget refusal (`n60_graph_set_rebuild_options`).
7. **Memory.** At 262,144 taps a stage holds about 2.1 MB of filter spectra plus about 2.1 MB of
   history per lane, and twice that during a rebuild. A 16-lane layout with per-lane filters is about
   140 MB at peak, inside `kMaxArenaBytes` (2 GiB, `snapshot.cpp:33`). Arena pages are touched on
   the control thread at build, never first touched in the callback.
8. **Accuracy.** Against a double-precision direct convolution, the output error is at most -110 dB
   relative to the output RMS (white noise, and an exponentially decaying random filter) at every
   tap-count boundary. The graph with `firScheme` 1 matches the legacy kernel's `N60Convolution` on
   the same 262,144-tap stereo program within -110 dBFS peak. The G2 goldens are unchanged with the
   flag off.
9. **Protection per output** (owner, Q4). Two layers on every output:
   - *User protection* (limiter, true-peak guard, soft clip, rider, as in the stereo chain). By
     default program lanes form one linked PROTECTION group (it preserves the image) and each sub
     lane has its own stage with the program settings. An Advanced switch, "Independent per
     output", gives every program lane its own stage. Per-output overrides: ceiling (live) and
     on/off. Look-ahead and oversampling are shared, so all outputs have the same latency in both
     modes, and switching modes is a topology rebuild with the standard fade.
   - *Hard limit*, always on in both modes and not affected by the user's on/off: one unlinked
     PROTECTION stage per output, last before FINAL_SANITISE, with the layout safety limiter's
     parameters (limiter on, -1 dBFS ceiling, no look-ahead or oversampling, so zero latency;
     `core/src/layout.cpp:276–278`), replacing that single linked stage. The user ceiling is
     clamped to at most the hard ceiling.
   Routed outputs (E8) keep their per-output stages and gain the hard limit. With
   `e9.output-protection` off the graph is bit-identical to today.
10. **Headroom assistant.** New core design maths `core/include/n60/headroom.h` (C ABI, not on the
    audio path, Linux CI) evaluates each output lane's composite magnitude from the stage
    descriptors Swift already publishes: PEQ and shelves analytically, FIR, room and speaker IR by
    FFT, bass-management sums into each sub (owner, Q3: the front pair adds coherently, other
   redirected lanes add as power; a Strict option adds every lane coherently), sub EQ, gain and polarity, dynamic EQ at maximum
    boost, compressor make-up, on a 1/48-octave grid from 10 Hz to 0.45 fs. It returns the peak
    gain, its frequency, and a true-peak margin (+0.5 dB at 4× oversampling) for each output. Swift
    shows "needs N dB" per output and offers Apply, which sets a per-output trim through the live
    OUTPUT_GAIN path (ramped), with Undo. The stereo kernel's automatic headroom stays as it is
    until E23.
