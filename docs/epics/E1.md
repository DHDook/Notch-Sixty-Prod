## Slices

### S1 `e1/feature-flags`: lightweight flag mechanism

- [x] Add `NotchSixty/State/FeatureFlags.swift`:
  - `enum FeatureFlag: String, CaseIterable`, one case per in-flight epic, each with a title and an owning epic;
  - a `FeatureFlags` store over an injectable `UserDefaults` (keys `feature.<rawValue>`);
  - an `isEnabled(_:)` check.
- [x] Defaults are compiled in and off. **Debug** builds can turn flags on in a "Developer" section of Settings. **Release** builds ignore stored overrides unless launched with `-NotchSixtyFeatures <list>` (for TestFlight testers), so unfinished work never shows in a shipped build by accident.
- [x] The engine never reads flags. Swift decides, then publishes the configuration through the existing graph/snapshot path, so the C/C++ core stays flag-free and portable (E21).
- [x] Move the existing toggles' string keys into one `PreferenceKeys` namespace. Same key strings, so no migration is needed.
- [x] Tests:
  - defaults are off;
  - Debug overrides persist;
  - Release ignores stored overrides and honours the launch argument;
  - unknown keys are ignored.
- [x] Document it in `CLAUDE.md` ("Build one slice per branch … behind the epic's feature flag") and in a short `docs/FEATURE_FLAGS.md`.
