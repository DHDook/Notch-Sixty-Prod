# E1 Trunk, CI and docs hygiene

**Status:** plan approved 17 Oct 2026. S1 (`e1/feature-flags`) in review.

## Goal

`main` is a trustworthy trunk:

- unfinished epics merge dark behind feature flags;
- CI is three workflows that test behaviour, not source text;
- the docs describe the current design.

Done when the program plan's E1 line holds: "text validators retired, 3 workflows, living docs current".

Feature flag: none. E1 builds the flag mechanism; its own slices don't need one.

## Slices

### S1 `e1/feature-flags`: lightweight flag mechanism

- [ ] Add `NotchSixty/State/FeatureFlags.swift`:
  - `enum FeatureFlag: String, CaseIterable`, one case per in-flight epic, each with a title and an owning epic;
  - a `FeatureFlags` store over an injectable `UserDefaults` (keys `feature.<rawValue>`);
  - an `isEnabled(_:)` check.
- [ ] Defaults are compiled in and off. **Debug** builds can turn flags on in a "Developer" section of Settings. **Release** builds ignore stored overrides unless launched with `-NotchSixtyFeatures <list>` (for TestFlight testers), so unfinished work never shows in a shipped build by accident.
- [ ] The engine never reads flags. Swift decides, then publishes the configuration through the existing graph/snapshot path, so the C/C++ core stays flag-free and portable (E21).
- [ ] Move the existing toggles' string keys into one `PreferenceKeys` namespace. Same key strings, so no migration is needed.
- [ ] Tests:
  - defaults are off;
  - Debug overrides persist;
  - Release ignores stored overrides and honours the launch argument;
  - unknown keys are ignored.
- [ ] Document it in `CLAUDE.md` ("Build one slice per branch … behind the epic's feature flag") and in a short `docs/FEATURE_FLAGS.md`.

### S2 `e1/three-workflows`: collapse 82 workflows into three

- [ ] `pr.yml`, the fast PR check, on every PR to `main`:
  - a Debug build of `NotchSixty` (xcode-27);
  - the behavioural C harnesses that still pass, run with clang under `-Werror`;
  - the PR35 rendered-transition harness.
  - Target: under 10 minutes.
- [ ] `macos-full.yml`, the full macOS build and test, on push to `main`, on PRs labelled `full-ci`, and on manual dispatch:
  - full Debug XCTest;
  - Release `NotchSixty-Performance` build;
  - the PR35 render benchmarks.
  - This replaces `macos.yml`.
- [ ] `release.yml`, manual, from `release-dmg.yml`:
  - version check, tests, Release build, ad-hoc sign, entitlements check, DMG, SBOM, package manifest.
  - Keep the useful RC checks from `final-integrated-rc-qa.yml` and `pr114-*`; drop their stacked-PR ancestry checks.
- [ ] Delete the other 79 workflows, including `hardware-test.yml` once its packaging job is folded into `release.yml`.
- [ ] Before deleting, list every behavioural harness the deleted workflows ran. Each one ends up in `pr.yml`, in an XCTest, or recorded as obsolete in the PR description.
- [ ] Logs go to `$RUNNER_TEMP`, not `/tmp`.

## Tests and checks

- S1: new XCTests, plus the full suite.
- S2/S3:
  - full XCTest locally;
  - each new workflow observed green on a real PR or run;
  - a dry run of `release.yml` from dispatch (it doesn't publish anything).
- S4: link check across `docs/`, `README.md` and `CLAUDE.md`.
- E1 has no bench checks.

## Risks

- Deleting a workflow can hide a behavioural harness that nothing else runs. S2's inventory step exists to prevent that.
- `release.yml` can only be fully proven by a real release dispatch; the first one needs watching.
